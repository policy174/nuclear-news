   - **명세 12장의 브랜치 분리는 S2부터 지킨다**: `feat/p1-ranking` · `feat/p2-copy` · …

## S1. features 결손 해소 — 명세에 없지만 최우선

### 왜 여기 있나

| 결손이 남으면 | 결과 |
|---|---|
| Phase 1-1 임계값 | 결손 면제로 덮은 채 14.0을 정하게 된다. **결손이 고쳐지면 분포가 바뀌어 재산출 필요** — 임계값을 두 번 정한다 |
| Phase 1-4 선정 사유 | 입력 factor가 실질 2값이라 템플릿을 3종으로 늘려도 재진술. `a64e252`가 되돌린 그 자리로 돌아간다 |
| 등급 신뢰도 | `must_read`의 40%가 LLM 판정이 아니라 출처로 자동 부여된 값 |

### 작업

1. **큐에 들어가기 전에 잡는다** ← 실효 지점 (구현 완료, `aa3315d`)

   `curation_errors()`(`data_quality.py:278`)가 **`features`를 검사하지 않아**(실측: 결손
   payload도 `[]` 반환) 결손 응답이 완결된 것으로 통과했다.

   **되돌릴 수 없게 되는 지점은 큐 적재다.** 기사는 큐에 들어가는 순간 `state["sent"]`에
   마킹되고 `article_seen()`(`news_bot.py:408`)이 재수집을 막는다 — 실측으로 결손 캐시
   20건 전부가 `sent`에 있다. 그 뒤에는 어떤 재큐레이션 경로로도 도달하지 못한다.

   **수정**: `curation_errors()`에 `require_features` 플래그 신설 → `curate_batch()`
   응답 검증에서만 켠다. 결손 응답은 재생성 대상이 된다.
   플래그를 기본값 False로 둔 이유: 아카이브 적재·배포 게이트는 '게시 자격' 판정이라
   features 없이도 통과해야 한다. 켜면 결손 기사가 아카이브에서 통째로 빠져
   트렌드·`prior_coverage` 재료가 사라진다.

   > 초판에서 "재큐레이션이 안 걸려 같은 10건이 매 회차 재등장한다"고 썼는데 **틀렸다.**
   > 반복 등장은 **큐 3일 보존**(`news_bot.py:1366`) 때문이다.

2. **폴백의 등급 자동 승격 중단** — 구현 완료 (`fallback_curation()`)
   - 기존: batch 실패 + `is_tier1_source()` → `must_read` 자동 부여, `features` 없음
   - 변경: 등급을 올리지 않는다. 이 레코드는 곧바로 `_legacy_score()`로 빠지므로
     승격은 "큐레이션이 실패한 1차 출처"를 `must_read`에 섞는 경로였다

3. **2차 방어선** — `needs_recuration()` 구현 완료
   `features` 결손도 재큐레이션 대상으로 본다. 위 `sent` 마킹 때문에 큐에 못 들어간
   격리분·`sent` 만료(14일)분에만 도달하는 보조 장치다. `FEATURES_RETRY_LIMIT=2`로
   무한 재질의를 막는다. **현재 캐시 697건 기준 재큐레이션 대상 순증 0건 — 추가 비용 없음.**
4. **결손률 로깅** — 지금은 흔적이 0이다.
   - crawl 로그 1줄 + `selection_stats`에 `features_missing` 필드 추가
   - 이게 없으면 고쳐졌는지 판단할 방법이 없다
5. **관찰 2주** — 신규 수집분 결손률 **5% 미만** 유지

### 수용 기준 (배포 후 관찰)

- [ ] 신규 수집분 `features` 결손률 < 5% (2주 연속)
- [ ] batch 실패가 `must_read`를 만들지 않음
- [ ] 결손률이 로그·`selection_stats` 양쪽에 남음
- [ ] `score_distribution.md` 재산출 시 `must_read` 이봉 분포가 단봉으로 수렴

### 배포 첫날 확인할 것

코드만으로는 성패를 알 수 없다. 배포 후 아래 셋을 눈으로 봐야 한다.

| 어디서 | 무엇을 | 나쁜 신호 |
|---|---|---|
| crawl 로그 마지막 줄 | `features_missing=N (x%)` | 비율이 이전 수준(10%+)에서 안 내려감 |
| crawl 로그 | `! 품질 게이트 재생성: N건` 빈도 | 매 chunk 재생성 = 프롬프트가 features를 못 받고 있음 |
| `delivery_log.jsonl` | `record_type:selection_stats` 줄의 `features_missing` | 지역별로 계속 0이 아님 |

`selection_stats`는 **아직 실제 로그에 0줄**이다(`AS_IS.md` §5) — 첫 `daily-brief` 실행이
이 계약의 첫 검증이다. 줄이 안 생기면 `append_selection_stats()` 경로부터 본다.

## S2. 랭킹 신뢰도 (명세 Phase 1) — 대부분 이미 구현됨

### 2-1 선정 하한 — `9918e9c`에 구현됨. 고칠 것 2가지

1. ✅ **등급 면제 제거** — `72ce421`. 면제는 `features` 결손 1종만 남았다.
   검증: 20회차 재점수화로 두 판정의 선정 집합 비교 → **139건 동일, 차집합 0**.
   `must_read`에도 14.0을 거는 더 엄격한 설정으로도 139건 그대로다(미달 `must_read`가
   전부 결손 면제에 걸린다).
2. ⏸ **임계값 재산출** — **S1 관찰 후에 한다.** 결손이 줄면 legacy 봉우리가 사라져
   분포가 통째로 바뀐다. 지금 재산출하면 두 번 하게 된다.
   `scratchpad/extract_pool.py` → `analyze_pool.py` 재실행. 목표는 그대로 **주 1~2회 0건**

### 2-2 에디터 픽 0~2건

명세는 **자동** 0~2건을 요구한다. 그런데 `34f2b81`이 **수동** `selection_overrides.json`을
이미 넣었다. 역할이 겹친다.

> **결정 필요**: 자동 에디터 픽을 만들 것인가, 수동 override로 갈 것인가, 둘 다인가.
> 둘 다면 우선순위 규칙(수동이 자동을 이기는가)을 정해야 한다.

### 2-3 사건 단위 병합 — 확인만

이미 있다: 임베딩 0.92 + 시설·국가 충돌 차단(`build_data.py:943`) + 회색지대 LLM
검수(`issue_review.py`). 명세가 요구한 것 중 확인할 것:
- 대표 기사 선택 규칙이 **공식 원문 > 1차 보도 > 후속 보도** 순인가
- 병합 근거가 데이터로 남는가 → `issue_audit.json`에 있음. 화면 노출 여부만 결정

### 2-4 선정 사유 — **품질 게이트 통과 전 착수 금지**

"S1 끝나면"으로만 두면 Phase 1에서 다시 주관적으로 판단하게 된다. **수치 게이트**로 박는다
(값은 확정이 아니라 착수 전 승인 대상):

| 게이트 | 기준 | 왜 |
|---|---|---|
| features 결손률 | 고유 기사 기준 **< 10%** | 입력이 없으면 사유도 없다 |
| feature 값 편중 | 어느 feature도 단일 값이 **< 75%** | 지금 `korea_relevance` 58.7% · `report_worthiness` 62% |
| 사유↔분류 중복률 | 생성 사유 문구와 `category`·`event_type` 라벨의 단순 중복 **< 50%** | `a64e252`가 되돌린 실패 모드 |
| 상위 조합 집중 | 최빈 사유 조합이 전체의 **< 15%** | 실측 '정책 결정/정책 영향 큼' 22% |
| legacy 식별 | legacy 경로 항목이 상태 화면·로그에서 구분 가능 | 사유를 만들 수 없는 항목을 조용히 통과시키지 않기 |

통과하면 규칙 기반 3종 템플릿 + 직전 2일 회피를 구현한다.

`sensitivity_level`은 **전체 검색 0건**이다. 명세는 스키마만 쓰면 되는 것처럼 읽히지만

**누락 시 기본값 3(전체 중립)** 은 명세대로 유지한다 — 안전한 쪽으로 실패해야 한다.

## S6. 유머 문구 활성화 — S5 통과 후 1시간

명세는 Phase 2에서 유머 문구를 넣고 Phase 4에서 통제하라고 한다. **순서를 뒤집는다.**

명세 P5는 *"유머는 코드로 통제한다 — 민감도 등급에 따라 자동 비활성화"* 인데,
`sensitivity_level`이 없는 상태에서 유머를 켜면 **자동 비활성화가 구조적으로 불가능**하다.
사고·인명 피해 기사 옆에 "오늘은 조용합니다"가 뜨는 사고가 Phase 2~4 사이 내내 열려 있다.

S5가 끝나면 `copy.json`의 `tone: "humor"` 4건을 켜고 화면당 상한 2개를 적용한다.
`fallback_neutral`은 S3에서 이미 다 채워져 있으므로 스위치만 켜는 작업이다.

## S7. 사건 추적 (명세 Phase 5) — 별도 트랙

착수 전 **데이터 출처를 먼저 정해야 한다.** `web/public/data/`는 gitignore라 어제가 없다
(`AS_IS.md` C7). 두 선택지:

| 안 | 방법 | 비용 |
|---|---|---|
| A | 매 빌드에 어제 이슈를 `archive`+`delivery_log`에서 재구성해 비교 | 빌드 시간 증가, 병합 결과가 흔들리면 델타도 흔들림 |
| B | 이슈 클러스터 결과를 커밋되는 파일로 저장(사건 ID 지속성) | 명세 5-1이 요구하는 것과 동일. 초기 비용 크지만 정답 |

**B 권고.** A는 5-1(사건 ID 지속성)을 어차피 다시 하게 된다.
