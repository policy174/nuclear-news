## 한 줄 결론

**웹에 내용이 없는 게 아니라, 있는 내용이 잘못된 이름표를 달고 있거나 더 좋은 쪽이
버려지고 있다.** 새 필드를 만들기 전에 이미 만들어 둔 것부터 제대로 내보내야 한다.
아래 P0·P1 은 새 LLM 호출 0회로 처리된다.

## P0 — 같은 문장이 텔레그램에서는 '한수원 시사점', 웹에서는 '산업 영향'

같은 `implication` 필드다. 실측(2026-08-02 발송분과 웹 8/3 화면 대조):

| | 라벨 | 문장 |
|---|---|---|
| 텔레그램 | 🇰🇷 **한수원 시사점** | 과거 탈핵 정책 주장의 현실적 타당성을 재검토하는 계기가 될 수 있습니다. |
| 웹 | **산업 영향** AI | (글자까지 동일) |

큐레이션 프롬프트의 정의도 "AI 해석인 시사점"이지 '산업 영향'이 아니다
(`news_bot.py` BATCH_SUFFIX). 웹 라벨이 **이 서비스의 정체성(한수원 임직원용)을 지운다** —
"다른 사이트와 뭐가 다른지 모르겠다"의 직접 원인으로 본다.

**할 일**: 웹 라벨을 `한수원 시사점`(또는 `우리 부서 관점`)으로 바꾼다.
`web/public/app.js` 의 `issueDetailModel().impact.label`, 선두 카드, 사이드 근거 패널이
같은 값을 쓰므로 한 군데만 고치면 된다. 데이터 변경 0.

**주의**: 라벨을 바꾸면 그 문장이 AI 해석이라는 표시(`AI` 배지)는 반드시 유지할 것.
한수원 이름을 붙이는 순간 공식 견해로 오해될 여지가 커진다.

## P0 — '왜 중요'(`why_important`)가 웹에서 사실상 죽어 있다

아카이브 681건 실측. `why_important` 는 must_read 전용이고 **150자 분석관 톤**,
`implication` 은 nice_to_know·must_read 겸용 **60자**다. 서로 다른 축이다
(`app.js` 주석도 그렇게 적혀 있다).

그런데 `web/build_data.py:2270,2392` 가 둘을 하나로 뭉갠다:

```python
"implication": representative.get("implication") or representative.get("why_important") or ""
```

must_read 55건 결과:

| 상태 | 건수 | 화면에서 벌어지는 일 |
|---|---|---|
| 둘 다 있음 | **22** | 110자 분석관 톤이 버려지고 60자만 표시 |
| `why_important` 만 | **19** | '산업 영향' 라벨로 **잘못** 표시 |
| `implication` 만 | **1** | 정상 |
| 둘 다 없음 | 13 | — |

**정상은 55건 중 1건이다.** 버려지는 쪽 예시:

> (버려짐, 110자) 유럽투자은행의 대출 승인은 루마니아 체르나보다 원전 1호기 개보수 사업의
> 주요 재원 조달이 확정되었음을 의미합니다. 이는 해당 원전의 계속운전 및 유럽 내 원전
> 사업 추진에 중요한 이정표가 됩니다.
>
> (표시됨, 60자) EIB의 대출 승인은 루마니아 원전 개보수 사업의 재정적 안정성을 확보하며
> 사업 추진에 탄력을 줄 것입니다.

**할 일**: `build_data` 가 두 필드를 **각각** 이슈 행에 실어 보내고, 화면이 둘을 별도
블록으로 세운다. 선두 카드는 이미 블록 구조라 자리가 있다:

```
무슨 일        summary
왜 중요        why_important   ← must_read 에서 75% 채워져 있다
한수원 시사점   implication
```

새 LLM 호출 0회. 이미 만들어 둔 문장을 꺼내는 것뿐이다.

**주의**: 두 블록이 같은 말을 되풀이하는 날이 있을 것이다(22건이 둘 다 보유).
`latest_change` 중복 억제와 같은 방식(자카드/포함률)으로 겹치면 한쪽을 숨길 것.

## P1 — 텔레그램에만 있는 것 2개

### ① 📝 보고서 검토 추천

발송분 실물:

> **📝 보고서 검토 추천 (2026-08-03)** — 오늘 동향 중 부서 보고서로 다룰 만한 사안
> 1. 중국 신규 원전 8기 건설 승인에 따른 글로벌 원전 시장 및 한국 원전 정책 함의
>    • 왜: …
>    • 추천 각도: 중국 원전 산업의 기술 자립도 및 수출 경쟁력 변화 전망 / …

**원자력정책실 업무에 가장 직결되는 기능인데 웹에 없다.** "다른 뉴스 사이트와 뭐가
다른가"에 대한 가장 강한 답이 이것이라고 본다 — 뉴스가 아니라 *내 다음 보고서 소재*다.

데이터는 이미 `outbox.json` 의 `briefs` 에 있다. 웹이 안 읽을 뿐이다.

### ② 💰 투자 관점

`daily_brief.py` 가 발송 시점에 별도 Gemini 호출로 구조화 필드(theme·mechanism·수혜유형·
시계·confidence)를 뽑아 Python 이 문장으로 조립한다. **웹 빌드는 이걸 읽지 않는다.**

이건 버그가 아니라 **의도적 결정**이다 — MVP 기획 때 "회사 서비스가 투자 시그널을 주는
모양새가 위험" 이라 숨기기로 했다. 되살릴지는 판단이 필요하고, 되살린다면 접근제어
결정과 묶여야 한다.

## P2 — 이미 알고 있고 데이터를 기다리는 것

### `open_question` 0%

- 배치 템플릿 결함은 `c82a09f` 로 해소. 이후 must_read 6건 중 1건 생성(17%).
- 아카이브 must_read 55건 중 **49건(89%)은 필드 도입 이전**이라 재큐레이션 없이는 영영 빈다.
- `open_question` 은 must_read 전용이고 웹 이슈의 27% 가 must_read 다. 다만
  **선두 카드는 17일 중 13일이 must_read** 라 이 블록은 선두에서만 의미가 있다.
- 2026-08-04 에 진단을 살렸다: 게이트 사유가 아카이브 레코드(`open_question_reject`)에
  실리고, crawl 이 `delivery_log.jsonl` 을 커밋한다(그 전까지는 러너와 함께 버려졌다 —
  커밋된 173건이 전부 발송 기록이었다).

**다음 세션 첫 명령**: 크롤 두어 번 돈 뒤

```bash
git fetch origin && git show origin/main:archive/2026-08.jsonl | python -c "import sys,json,collections; print(collections.Counter(json.loads(l).get('open_question_reject') or 'PASS' for l in sys.stdin if l.strip() and json.loads(l).get('importance')=='must_read'))"
```

`llm_null` 다수 → 프롬프트 / `no_source` 다수 → 근거 지목 지시 강화 / `forecast`·`is_question`
다수 → '완결형 서술문' 지시가 안 먹힘. **생성률을 KPI 로 삼지 말 것** — 게이트를 풀면
AI 가 미확정 사항을 지어낸다. 표본이 하루 3~6건이라 판단에 2~3일 필요.

### 히어로 종합 문장(`synthesis`) 0/17

`daily_lead.py` 는 돌고 있고 `daily_leads.json` 에 문장도 있다. 다만 8/3 생성분이

2026-08-04 에 히어로를 58→30px 로 줄여 **증상은 가렸지만 원인은 그대로**다. 종합 문장을

## Atlas — 언제 시작하나

**코드가 자동으로 판정한다.** `web/build_data.py: atlas_readiness()` 가 매 빌드마다
`meta.json` 에 상태를 쓴다. 지금:

```
open_question      0    (기준: ≥ 1건)        ← 미달
related_articles   7%   (기준: ≥ 20%)        ← 미달
implication        60%
latest_change      3%
official_source    6%
full_path_issues   0    (5칸 다 채운 이슈)
ready: false   blocking: ["open_question", "related_articles"]
```

즉 **Atlas 는 일정 문제가 아니라 데이터 문제다.** 두 관문이 열리기 전에 화면을 만들면
빈 그래프가 나온다. 확인은 이 한 줄:

```bash
curl -s "https://nuclens.pages.dev/data/meta.json?cb=1" | python -c "import sys,json; print(json.load(sys.stdin)['atlas_readiness'])"
```

- `open_question` 은 위 P2 작업으로 곧 1건 이상이 될 가능성이 높다.
- `related_articles` 20% 가 진짜 관문이다(현 7%). 이건 이슈 클러스터링이 기사를 얼마나
  묶느냐의 문제라, 임계값·병합 검수 쪽 작업과 같은 줄에 있다. **추정**: 여기가 가장
  오래 걸린다.

시안·계획은 이미 있다 — `~/.claude/plans/a-issue-atlas-cozy-lagoon.md` rev.2 (승인됨).
시안이 '신규'라고 한 것 중 팔레트와 우측 근거 패널은 이미 배포됐고, **남은 진짜 신규는
이슈 지도 메뉴 하나**다.
