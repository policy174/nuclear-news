**한 일**: 웹 라벨을 **`시사점`** 으로 바꿨다. 회사 이름은 붙이지 않는다 —
사용자 결정(2026-08-04): AI 해석에 기관명을 얹으면 공식 견해로 읽힐 여지가 커진다.

같이 정리한 것: 같은 필드를 다이얼로그는 `Nuclens 해석`이라 부르고 있었다. 한 필드에
이름이 셋(산업 영향·Nuclens 해석·시사점)이면 화면마다 다른 것으로 읽힌다 — 셋 다
`시사점` 하나로 합쳤다.

`AI` 배지는 렌더 지점(근거 패널·다이얼로그) 전부 그대로 유지했고,

## P0 — '왜 중요'(`why_important`)가 웹에서 사실상 죽어 있다 ✅ 처리됨

아카이브 681건 실측. `why_important` 는 must_read 전용이고 **150자 분석관 톤**,
`implication` 은 nice_to_know·must_read 겸용 **60자**다. 서로 다른 축이다
(`app.js` 주석도 그렇게 적혀 있다).

그런데 `web/build_data.py:2270,2392` 가 둘을 하나로 뭉갠다:

```python
"implication": representative.get("implication") or representative.get("why_important") or ""
```

must_read 55건 결과:

| 상태 | 건수 | 화면에서 벌어지는 일 |
|---|---|---|
| 둘 다 있음 | **22** | 110자 분석관 톤이 버려지고 60자만 표시 |
| `why_important` 만 | **19** | '산업 영향' 라벨로 **잘못** 표시 |
| `implication` 만 | **1** | 정상 |
| 둘 다 없음 | 13 | — |

**정상은 55건 중 1건이다.** 버려지는 쪽 예시:

> (버려짐, 110자) 유럽투자은행의 대출 승인은 루마니아 체르나보다 원전 1호기 개보수 사업의
> 주요 재원 조달이 확정되었음을 의미합니다. 이는 해당 원전의 계속운전 및 유럽 내 원전
> 사업 추진에 중요한 이정표가 됩니다.
>
> (표시됨, 60자) EIB의 대출 승인은 루마니아 원전 개보수 사업의 재정적 안정성을 확보하며
> 사업 추진에 탄력을 줄 것입니다.

**한 일**: `build_data.split_interpretation()` 이 두 필드를 각각 이슈 행에 싣고,
화면이 둘을 별도 블록으로 세운다. 선두 카드·근거 패널·다이얼로그 셋 다:

```
무슨 일        summary
왜 중요한가    why_important
시사점         implication
```

새 LLM 호출 0회. 재빌드 후 실측 — 브리핑 이슈 카드 127개 기준:

| | 건수 | 이전 화면 | 지금 |
|---|---|---|---|
| 둘 다 | 15 | 짧은 쪽만 | 두 블록 |
| `implication` 만 | 46 | 정상(라벨만 틀림) | 시사점 |
| `why_important` 만 | 16 | **'산업 영향'으로 오표기** | 왜 중요한가 |
| 둘 다 없음 | 50 | — | 블록 없음 |

**중복 억제는 넣었지만 거의 안 걸린다 — 이게 다음 작업거리다.** 겹치면 긴 쪽만
남기도록 `_is_restatement`(자카드 0.45 / 포함률 0.8)를 태웠는데, 아카이브 전체에서
둘 다 가진 22건 중 **1건만** 걸렀다. 자카드 최댓값이 0.30 이고 0.07까지 연속 분포라
임계값을 낮춰도 잘리는 지점이 없다(0.25 로 내리면 1→6 건으로 튄다). 손으로 맞추면
노이즈를 학습하는 것이라 공용 기본값을 그대로 뒀다.

실제 증상은 **첫 절의 되풀이**다:

> 왜 중요한가  미국 에너지부의 시험용 원자로 가동 승인은 차세대 원자로 기술 개발의
>              중요한 이정표이며, 향후 SMR 및 마이크로 원자로 상용화에 긍정적…
> 시사점       오클로의 시험용 원자로 가동 승인은 차세대 원자로 기술 개발 및
>              상용화에 중요한 진전입니다.

두 문장은 같은 LLM 호출이 같은 기사로 만든다. 표시 단계에서 가릴 문제가 아니라
**큐레이션 프롬프트가 "두 필드는 서로를 되풀이하지 말 것"을 지시하지 않는 문제**다.
고칠 자리는 `news_bot.py` 의 BATCH_SUFFIX 이고, 요약 종결어미 게이트(아래 P2)와
같은 줄에 있다 — 프롬프트를 한 번 열 때 같이 손대는 게 맞다.

## P1 — 텔레그램에만 있던 것 2개 (둘 다 결정 완료)

### ① 📝 보고서 검토 추천 ✅ 처리됨 (라벨 형태)

발송분 실물:

> **📝 보고서 검토 추천 (2026-08-03)** — 오늘 동향 중 부서 보고서로 다룰 만한 사안
> 1. 중국 신규 원전 8기 건설 승인에 따른 글로벌 원전 시장 및 한국 원전 정책 함의
>    • 왜: …
>    • 추천 각도: 중국 원전 산업의 기술 자립도 및 수출 경쟁력 변화 전망 / …

**원자력정책실 업무에 가장 직결되는 기능인데 웹에 없다.** "다른 뉴스 사이트와 뭐가
다른가"에 대한 가장 강한 답이 이것이라고 본다 — 뉴스가 아니라 *내 다음 보고서 소재*다.

**한 일 (2026-08-04): 라벨 하나로 냈다.** 사용자 결정 — 섹션이 아니라 라벨.
`📝 보고서 검토 추천` 배지가 선두 카드·이슈 카드·근거 패널·다이얼로그에 붙고,
추천 주제는 `title` 툴팁으로만 보인다. **'왜'와 '추천 각도'는 웹에 내지 않는다** —
그건 개인 브리핑의 판단이고, 웹은 동료가 함께 보는 화면이다. 무엇이 후보인지는
공유해도 어떻게 쓰라는 조언까지 화면이 대신 말할 자리는 아니다.

경로(새 LLM 호출 0회):

```
daily_brief.plan_briefs  추천 hash→주제를 기사 메타에 실음 (report_pick)
  → delivery_log.jsonl   confirm 이 적재, 크롤이 커밋 → 날짜별로 남는다
  → build_data           delivery 조인해서 이슈 행에 올림 (pick_report_topic)
  → app.js               reportPickBadge()
```

`outbox.json` 을 직접 읽지 않은 이유: **매일 덮어쓴다.** 어제 추천을 알 방법이 없어
과거 브리핑을 열면 배지가 사라진다. `delivery_log` 는 append-only 라 날짜별로 쌓인다.

**단, 오늘까지의 추천은 배지가 안 붙는다.** `delivery_log` 는 append-only 라 기존
줄을 고쳐 소급 적용할 수 없다(고치면 `merge=union` 전제가 깨진다). 8/3 추천
1건(`538c53ac`)은 `outbox.json` 의 `report_diag` 에만 남아 있다. **다음 daily-brief
실행분(내일 07:25 KST)부터 화면에 뜬다.**

곁가지로 `report_diag.recommended[].hash` 의 8자 절단을 풀었다 — 이게 조인 키라
잘려 있으면 `delivery_log` 와 안 붙는다.

### ② 💰 투자 관점 — 안 낸다 (결정 완료)

`daily_brief.py` 가 발송 시점에 별도 Gemini 호출로 구조화 필드(theme·mechanism·수혜유형·
시계·confidence)를 뽑아 Python 이 문장으로 조립한다. **웹 빌드는 이걸 읽지 않는다.**

이건 버그가 아니라 **의도적 결정**이었고, 2026-08-04 사용자가 그대로 유지하기로 했다 —
"투자 관점은 필요없을 듯". 접근제어 4단계 게이트 결정과의 연동도 함께 종료. 텔레그램
개인 브리핑에는 계속 나간다(코드 변경 0).

**되살릴 일이 생기면** 접근제어 결정이 선행돼야 한다는 조건은 그대로다 — 회사 서비스가
투자 시그널을 주는 모양새의 위험은 없어진 게 아니라 노출을 안 해서 안 생기는 것이다.

## Atlas — 언제 시작하나

**코드가 자동으로 판정한다.** `web/build_data.py: atlas_readiness()` 가 매 빌드마다
`meta.json` 에 상태를 쓴다. 지금:

```
open_question      0    (기준: ≥ 1건)        ← 미달
related_articles   7%   (기준: ≥ 20%)        ← 미달
implication        60%
latest_change      3%
official_source    6%
full_path_issues   0    (5칸 다 채운 이슈)
ready: false   blocking: ["open_question", "related_articles"]
```

즉 **Atlas 는 일정 문제가 아니라 데이터 문제다.** 두 관문이 열리기 전에 화면을 만들면
빈 그래프가 나온다. 확인은 이 한 줄:

```bash
curl -s "https://nuclens.pages.dev/data/meta.json?cb=1" | python -c "import sys,json; print(json.load(sys.stdin)['atlas_readiness'])"
```

- `open_question` 은 위 P2 작업으로 곧 1건 이상이 될 가능성이 높다.
- `related_articles` 20% 가 진짜 관문이다(현 7%). 이건 이슈 클러스터링이 기사를 얼마나
  묶느냐의 문제라, 임계값·병합 검수 쪽 작업과 같은 줄에 있다. **추정**: 여기가 가장
  오래 걸린다.

시안·계획은 이미 있다 — `~/.claude/plans/a-issue-atlas-cozy-lagoon.md` rev.2 (승인됨).
시안이 '신규'라고 한 것 중 팔레트와 우측 근거 패널은 이미 배포됐고, **남은 진짜 신규는
이슈 지도 메뉴 하나**다.
